# SEO-качество и он-пейдж: эталонная база (РФ-рынок, Яндекс + Google)

> Дистиллят практики многосайтовой SEO-сетки на статейных/каталожных сайтах (РФ, Яндекс+Google).
> Не теория — рабочий чек-лист с обоснованием «почему», чтобы результаты разведки ниши превращались
> в конкретные решения по структуре сайта, шаблонам страниц и контент-плану.

## Как использовать этот файл

При переходе от анализа ниши к архитектуре сайта и контент-плану — сверяться с разделами ниже:
- Проектируешь шаблон страницы (title/description/H1) → раздел «Метатеги».
- Решаешь, как группировать запросы в статьи/страницы → раздел «Кластеризация: Soft vs Hard».
- Проектируешь URL-схему → раздел «Canonical, слаги, URL, дубли».
- Определяешь, какую разметку Schema.org заложить в шаблоны → раздел «Микроразметка».
- Пишешь промпт/ТЗ на генерацию статьи → раздел «Логика создания статьи».
- Проверяешь, что сайт не выглядит «пустым» для поисковика/пользователя → раздел «E-E-A-T».
- Планируешь ссылочную стратегию → раздел «Off-page».
- Финальная проверка перед стартом публикаций → раздел «Правила НИКОГДА» + «Чек-лист по категориям».

## 1. Метатеги (title / description / H1)

- **Title — не резать искусственно под 60 символов.** Ограничение в ~60 символов — это лишь
  вероятность, что вся строка целиком влезет в сниппет выдачи. Гораздо важнее уместить в title
  максимум уникальных, наиболее частотных слов из семантического кластера страницы. Если частотный
  ключ не влезает в 60 символов вместе с остальными словами — приоритет за частотным ключом, а не
  за формальной длиной.
- **Description — можно смело увеличивать до ~250 символов.** Жёсткое правило «до 160» — тоже
  вероятностное, не техническое. Поисковик всё равно чаще всего сам выбирает наиболее релевантный
  фрагмент текста под конкретный запрос пользователя и показывает его в сниппете вместо статичного
  description. Задача description — не влезть в лимит, а содержать релевантные формулировки, из
  которых поисковик может собрать сниппет.
- **Уникальность метатегов на каждой странице** — обязательна (title и description не должны
  повторяться между страницами шаблона: категориями, тегами, карточками).
- **H1 = самый частотный ключ кластера, поставленный ближе к началу заголовка** + добавление
  уникальных слов из семантической группы. H1 не должен дословно дублировать заголовки
  конкурентов из топ-10 — точное совпадение формулировки повышает риск попасть под фильтр
  неоригинальности контента.

## 2. Кластеризация: Soft vs Hard

Ключевой методологический момент, который часто теряется при переносе ТЗ с коммерческих страниц
на статейный контент.

- **Soft-кластеризация** — более широкая группировка запросов: в один кластер (и, соответственно,
  в одну статью) попадают близкие по смыслу и интенту формулировки, даже если они не являются
  строгими синонимами. Это единственный правильный метод **для статейных/блоговых материалов**.
  Hard-метод на статьях порождает избыточное количество почти идентичных кластеров → избыточное
  количество почти одинаковых статей → каннибализация запросов между своими же страницами.
- **Hard-кластеризация** — узкая, строгая группировка (запросы должны пересекаться по топу
  выдачи почти полностью). Подходит **только для коммерческих посадочных страниц** (страница
  услуги/товара/категории), где нужна максимальная точность соответствия страницы одному явному
  интенту, а не охват темы.
- Практическое правило: если строится информационная статья — по умолчанию Soft. Если строится
  коммерческая посадочная (услуга, категория каталога, лендинг конверсии) — Hard.
- На выходе разведки ниши это должно явно фигурировать в контент-плане: у каждого элемента плана
  (страница/статья) — пометка типа кластеризации, а не общий метод «на весь сайт».

### Логика сбора семантики (входной модуль для контент-плана)
1. Собрать сырые запросы по нише из источников частотности (Wordstat или аналог) + из отчётов
   поисковых консолей (Яндекс.Вебмастер / Google Search Console) за последние ~30 дней, если сайт
   уже что-то накопил.
2. Почистить (убрать мусорные/нерелевантные/слишком общие формулировки).
3. Сверить с уже использованными в существующем контенте (чтобы не плодить дубли кластеров).
4. Сгруппировать в кластеры нужным методом (Soft для статей, Hard для коммерции).
5. Сложить в бэклог контент-плана: кластер → тип страницы → точная частотность.

## 3. Canonical, слаги, URL, дубли

- **Canonical блога/статей — строго self-referencing** (страница указывает canonical сама на
  себя). Исключение — только осознанный анти-каннибализационный оверрайд, когда одна страница
  явно уступает вес другой, и это решение зафиксировано, а не возникло случайно из бага шаблона.
  ⚠️ **Частая причина, почему хорошо написанная статья не индексируется** — неверный canonical
  (случайно указывающий на чужую/другую страницу), из-за чего поисковик считает материал дублем.
  Проверять self-canonical нужно **на каждом типе шаблона отдельно**: статья, категория, тег,
  подборка/лендинг — баг в одном шаблоне не значит, что все остальные в порядке.
- **Слаги и URL — строго `^[a-z0-9-]+$`**: только латиница в нижнем регистре, цифры, дефис.
  Красные флаги: (а) Uppercase-символы в URL, (б) кириллица, попавшая в URL из-за сбоя
  транслитерации, (в) кириллические омоглифы — символы, визуально неотличимые от латиницы
  (например «а», «о», «е»), которые проходят мимо поверхностной проверки, но ломают
  маршрутизацию и превращают URL в кракозябры при шаринге. Транслитерацию нужно валидировать
  регулярным выражением по факту, а не полагаться на визуальное сходство результата.
- **Мусорные параметрические URL не должны индексироваться.** Любые параметры вида `?from=...`,
  `utm_source=...`, `yclid=...`, `gclid=...`, `ref=...` на посадочных страницах создают дубли в
  индексе — особенно у Google, где canonical интерпретируется как рекомендация, а не жёсткая
  команда. Фикс: (1) по возможности не генерировать такие параметры прямо в ссылках на сайте,
  (2) где параметр реально нужен — `noindex` + `Disallow` в robots.txt для параметрической версии +
  canonical на чистый адрес.
- **Теговые (и любые программно генерируемые) страницы не должны отдавать 404.** Частая грабля:
  список тегов/фильтров формируется без учёта тегов, реально присутствующих в базе (тег есть в
  перечне возможных значений, но ни разу не проставлен) → ссылка ведёт на 404. Чинить в **двух
  местах**: саму страницу (честный пустой стейт вместо 404) **и** алгоритм генерации списка ссылок —
  иначе проблема воспроизведётся на следующей партии контента. Если аудит находит целый класс URL с
  404 (систематическая поломка шаблона/генератора) — чинить генератор, а не страницы по одной.
- **robots.txt**: Disallow для мусорных/параметрических/служебных страниц. **Sitemap.xml**: без
  noindex-страниц и мусора — только то, что реально должно индексироваться.

## 4. Микроразметка (Schema.org / JSON-LD)

Список того, что стоит заложить в шаблоны сразу на этапе проектирования сайта.

### Обязательные / почти обязательные
- **Organization** — на главной (можно продублировать на «Контактах»): название/бренд, логотип, URL, соцсети, контакты.
- **WebSite** — только на главной: описание, URL, при наличии внутреннего поиска — `SearchAction`.
- **Article / BlogPosting / NewsArticle** — основная разметка материала. `Article` — универсальный, `BlogPosting` — для блога, `NewsArticle` — только для настоящего новостного раздела. Поля: `headline, description, image, author, publisher, datePublished, dateModified, mainEntityOfPage`.
- **BreadcrumbList** — хлебные крошки на всех страницах глубже главной.
- **Person** — автор материала (вложенный в Article либо отдельная страница). Поля: `name, image, url, sameAs`. Если авторов несколько — разметка обязательна.

### По необходимости
- **FAQPage** — на любой странице с реальным блоком «Частые вопросы». Даёт шанс на расширенный сниппет и лучше считывается ИИ-ответами (AEO) — работает и на SEO, и на видимость в ответах ИИ.
- **CollectionPage** — для страниц категории/рубрики/архива (предпочтительнее голого `Article`).
- **ItemList** — для списков/подборок/топов («10 лучших…»).
- **ImageObject** — для основной иллюстрации (обычно внутри Article).

### Ситуативные (только если реально применимо)
- **HowTo** — только пошаговые инструкции. **Product** — только товар с ценой/наличием. **Review** — полноценная экспертная оценка. **Service** — описание услуги. **Course** — обучающие курсы. **SoftwareApplication** — приложения/сервисы. **VideoObject** — встроенное видео. **QAPage** — не путать с FAQPage: только формат «вопрос пользователя → ответы других пользователей».

### Технические требования к разметке
- **`dateModified` — машиночитаемый** в JSON-LD, а не только визуальный текст «Обновлено: дата».
- **Валидация обязательна** после изменений шаблонов (Rich Results Test/аналог + консоль вебмастера) — до публикации на весь сайт.
- Проектирование: заранее прописать в ТЗ полный список типов разметки на каждый тип страницы.

## 5. Логика создания статьи (от кластера до готового текста)

Порядок шагов для одной статьи/кластера — пропуск шага напрямую отражается на позициях.

1. **Кластер + точная частотность.** Soft-кластеризованная группа запросов с реальной частотностью — формулировки строятся от данных, не «на глаз».
2. **LSI-слова.** По группе выделяется сопутствующая лексика (термины, которые реальные тексты используют рядом с целевым запросом) — вписывается естественно, не списком.
3. **2–3 конкурента из топ-10.** Страницы, реально ранжирующиеся по большинству запросов кластера — **отдельно в Яндексе и в Google** (наборы могут отличаться, проверять оба).
4. **Бенчмарк по конкурентам.** Средняя длина текста (целевая = средняя + запас), среднее число изображений (целевое = среднее +15%), наличие инфографики/таблиц (есть у конкурентов — делать обязательно).
5. **Заголовок (H1/Title).** Самый частотный ключ — ближе к началу + уникальные слова группы. Не дублировать дословно заголовки конкурентов.
6. **Структура — полнее лучшего конкурента.** Не копировать одного — собрать структуру полнее и логичнее, чем у любого по отдельности (дать модели свой H1 + структуры конкурентов и попросить собрать более полную версию).

Всё это — часть промпта/ТЗ на генерацию, а не постфактум-проверка.

## 6. E-E-A-T и доверие

- **Автор (byline)** на каждом материале — конкретное имя/роль, не «Редакция».
- **Реалистичный аватар автора** — фото живого человека, а не иконка-плейсхолдер.
- **Дата обновления** — видимая и машиночитаемая (`dateModified`).
- **Внутренние ссылки** — материал встроен в перелинковку, а не «сирота». У близких по теме статей — взаимная перелинковка.
- **Ссылка на авторитетный источник — особенно для YMYL** (деньги/здоровье/право/безопасность): из статьи ставить исходящую ссылку на трастовый ресурс/справочник/официальный источник. **Обязательна премодерация** списка кандидатов человеком.
- **Объём — ориентир ~1500 слов** для топа по инфо-запросу (реальный таргет — по бенчмарку конкурентов).
- **Блок FAQ** с разметкой `FAQPage` — сигнал E-E-A-T и путь к расширенному сниппету/нейро-ответам.
- **Реальные обложки в «Похожих статьях»** — не универсальная заглушка. Повышает CTR внутренней перелинковки.
- **CTA-баннеры внутри статьи — не заголовочными тегами.** «Оставить заявку»/«Подобрать»/«Узнать стоимость» рендерить как `<div>`/обычный блок, а не как `<h2>`–`<h4>` — заголовок CTA рвёт иерархию H1→H2→H3, которую поисковик использует для понимания структуры.

### Актуализация (защита от «протухания» в топе)
- Рефреш раз в **3–4 месяца**, минимум для самых трафиковых материалов:
  1. Видимая метка «Обновлено: {дата}» + обновлённый машиночитаемый `dateModified`.
  2. Лёгкая синонимизация `title`/`description` (смысл сохраняется, формулировка обновляется).
  3. Содержательное обновление тела текста — переписать абзац/добавить актуальные предложения, а не пустая правка ради даты.
- Смысл: поисковики понижают материалы, которые долго не менялись, даже если информация не устарела.

## 7. Off-page (ссылочная масса) — аккуратно, без спама

Off-page — **только вручную, с реестром и премодерацией**. Наращивание должно выглядеть органично и постепенно.

- **Сабмиты (каталожные ссылки)**: закупать пачками, но **каждый раз сверяться с реестром** — площадки повторяются от продавца к продавцу.
- **Статейные ссылки**: 3 месяца по ~7–10 ссылок/мес на тематических ресурсах и в региональных СМИ. Анкоры — преимущественно общие («подробнее», «источник», голый URL); точное коммерческое вхождение — не более 15–20%.
- **Крауд-ссылки**: для разбавления — 3 месяца по ~30–40/мес, преимущественно безанкорные.
- **Единый реестр площадок на весь проект/сетку** — не покупать повторно у разных подрядчиков.
- **Не пользоваться сервисами-переиндексаторами ссылок** — красный флаг для алгоритма (нетипичный паттерн обнаружения).
- **Не допускать резкого скачка объёма бэклинков** — читается как спам-сигнал сам по себе.
- **Старт off-page — не раньше 2–3 месяцев с появления домена** (ранний профиль на молодом домене — аномалия).
- **Долю анкорных (точное вхождение) ссылок держать минимальной**, особенно в первый год.

## 8. Правила «НИКОГДА» (жёсткие, без исключений)

Нарушение способно уронить не одну страницу, а весь сайт целиком.

1. **Никогда не линковать разные свои сайты между собой** dofollow-ссылками, если они одного владельца/сетки. Поисковики (особенно Яндекс) распознают сеть аффилированных доменов — санкция накрывает всю группу. Если перелинковка нужна — только `rel="nofollow sponsored"`.
2. **Никогда не превышать ~5 новых материалов в день** на один сайт (молодой/средний проект). Темп наращивать постепенно, без кратных скачков. Резкий скачок читается как автогенерация/скупка контента.
3. **Никогда не накручивать поведенческие факторы (ПФ)** — искусственные клики/визиты. Яндекс детектирует, откат после санкции долгий.
4. **Никогда не запускать автоматический линкбилдинг** (массовая закупка/генерация ссылок без модерации, PBN, аренда, «1000 ссылок за копейки»). Только вручную, с реестром и премодерацией.
5. **Никогда не пользоваться сервисами-переиндексаторами ссылок.**
6. **URL — только нижний регистр и латиница**; Uppercase/кириллица/омоглифы — red flag.
7. **AI-статьи в YMYL (деньги/здоровье/право/безопасность) — публиковать только после фактчека человеком.**
8. **Не использовать общий промпт/пайплайн генерации без адаптации под нишу.**

## 9. Сводный чек-лист по категориям (перед стартом публикаций)

| Категория | Что проверить |
|---|---|
| Индексация | Веб-аналитика подключена (с оглядкой на закон о ПДн); теговые/фильтр-страницы не 404; sitemap.xml без мусора; robots.txt закрывает параметрические URL; IndexNow/пинг переобхода настроен; консоли вебмастера (Яндекс+Google) в проде |
| Canonical/дубли | Self-canonical проверен на КАЖДОМ типе шаблона; параметрические URL закрыты |
| Семантика | Кластеризация Soft (статьи) / Hard (коммерция) явно по каждому элементу плана; частотность из реального источника |
| Логика статьи | 2–3 конкурента из топ-10 (Я+G) разобраны; бенчмарк длины/картинок снят; H1 не дублирует конкурентов |
| Метатеги | Title — максимум частотных слов; description до ~250; уникальность на каждой странице |
| Микроразметка | Organization+WebSite (главная), Article+BreadcrumbList+Person (материалы), FAQPage (где вопрос-ответ), валидация пройдена |
| E-E-A-T | Автор+аватар живого человека, dateModified машиночитаем, ссылки на трастовые источники (YMYL), объём по бенчмарку, CTA не в заголовках |
| Перелинковка | Нет статей-«сирот»; у близких статей — взаимные ссылки |
| Off-page | Реестр площадок ведётся; анкоры ≤15–20%; без переиндексаторов; без резких скачков; старт не раньше 2–3 мес |
| Актуальность | Рефреш раз в 3–4 мес: дата + мета + абзац по существу |
| Правила НИКОГДА | Ни одно из 8 правил не нарушено |
